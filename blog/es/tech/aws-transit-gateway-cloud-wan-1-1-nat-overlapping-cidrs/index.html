AWS Transit Gateway y Cloud WAN presentan 1:1 NAT para la interconexión de redes sin costura

AWS lanza 1:1 Soporte NAT para Transit Gateway y Cloud WAN, permitiendo una comunicación perfecta entre redes privadas con rangos de direcciones IP superpuestos, un gran boon para conectividad de nube empresarial.

Publicado 25 de octubre de 20264 min leernubes-platformas

Datos confirmados

AWS anunció el 2026-10-23 que AWS Transit Gateway y AWS Cloud WAN ahora apoyan gestionado uno a uno (1:1) Network Address Translation (NAT) directamente en sus archivos adjuntos. La capacidad se integra con el Portal de NAT privado regional y está disponible en todas las regiones comerciales de AWS donde operan Transit Gateway y Cloud WAN.

  • 1:1 NAT permite a las redes privadas con bloques interdominios sin clases (CIDR) que se comuniquen sin renumerar ninguna red, implementando un dispositivo NAT separado, o escribiendo reglas explícitas de tráfico de retorno.
  • Los clientes definen reglas de traducción de direcciones en un accesorio Transit Gateway o Cloud WAN, especificando el rango IP privado que cada fuente se traduce en CIDR.
  • La traducción se aplica automáticamente en ambas direcciones a través de Amazon VPC, AWS Site-to-Site VPN, AWS Direct Connect y dispositivos SD-WAN conectados a través de Transit Gateway Connect.
  • AWS opera, escala y administra la capacidad NAT como parte del accesorio; el cliente no implementa ningún dispositivo NAT separado.
  • La configuración es compatible con la consola de gestión AWS, la interfaz de línea de comandos AWS (CLI), los SDKs AWS y AWS CloudFormation.
  • El tráfico traducido puede ser monitoreado a través de las métricas de Amazon CloudWatch y eventos de Amazon EventBridge.
  • Los precios siguen el modelo de precios Amazon VPC; el anuncio dirige a los usuarios a la página de precios VPC para obtener detalles.
  • Las referencias de documentación incluyen las páginas de productos AWS Transit Gateway y AWS Cloud WAN y sus respectivas guías de desarrolladores.

Análisis técnico

La introducción de NAT gestionado 1:1 en Transit Gateway y Cloud WAN adjuntos aborda una limitación arquitectónica de larga data en redes de nube empresarial: la incapacidad de interconectar redes privadas que comparten espacio de dirección RFC 1918. Históricamente, este escenario obligó a las organizaciones a entrar en uno de los tres caminos indeseables: renumeración manual de IP (alto riesgo, alto esfuerzo), despliegue y mantenimiento de aparatos NAT de terceros (encabezamiento operativo, límites de escala), o enrutamiento complejo basado en políticas con manejo asimétrico de retorno (fragio, difícil de auditar). Al incrustar 1:1 NAT directamente en el plano de apego, AWS elimina la necesidad de cualquiera de estas soluciones para los tipos de apego soportados.

Desde una perspectiva operacional, la característica cambia la gestión del estado de NAT desde instancias de gestión del cliente o electrodomésticos virtuales a un servicio totalmente gestionado y de alcance regional. El anuncio confirma que la traducción se aplica automáticamente en ambas direcciones sin reglas separadas de retorno-traffic, lo que implica el comportamiento simétrico NAT manejado por el plano de control. Este diseño reduce el área de superficie para la desconfiguración errónea —una fuente común de fallas de conectividad en entornos híbridos y multicloud— porque la misma configuración de apego rige tanto la traducción de entrada como el egress.

La integración con el portal privado regional NAT sugiere que el plano de datos subyacente aprovecha la misma infraestructura NAT gestionada utilizada para la conectividad de Internet externa, pero reutilizada para la traducción interapartamento. Esto tiene consecuencias prácticas para el rendimiento y la disponibilidad: los clientes heredan las características horizontales de escalado y resiliencia zonal de la pasarela de NAT privada regional sin proporcionar capacidad explícitamente. Sin embargo, el anuncio no revela límites de rendimiento por acoplamiento, sobrecarga de latencia, o si la traducción se produce en la capa de red (L3) o incluye cartografía a nivel de puerto (L4). Estos parámetros afectarían a la planificación de la capacidad para cargas de trabajo de alto rendimiento, como la reproducción de datos o la analítica en tiempo real en los PCV fusionados.

Para los flujos de trabajo de infraestructura como código, el soporte a través de CloudFormation, CLI, SDKs y la consola significa que la característica se puede incorporar en los sistemas de implementación existentes sin nuevas herramientas. La capacidad de definir reglas de traducción por apego permite el control granular: un solo Transit Gateway puede interconectar docenas de VPCs y VPNs, cada uno con su propio mapeo de traducción, mientras que los apegos no superpuestos pasan el tráfico nativamente. Esta granularidad es valiosa durante las migraciones escalonadas o las integraciones de fusiones donde sólo un subconjunto de redes requieren traducción en cualquier momento dado.

Monitoreo a través de métricas de CloudWatch y eventos de EventBridge proporciona ganchos de observabilidad para alertar sobre errores de traducción, anomalías de volumen de tráfico o cambios de salud adjuntos. El anuncio no enumera los espacios de nombres métricos específicos o los patrones de eventos de EventBridge, por lo que los equipos tendrán que consultar la documentación actualizada para construir paneles y automatización. La ausencia de estos detalles en las notas de liberación es una brecha que los operadores deben validar durante el estancamiento de despliegues.

  • Elimina la necesidad de aparatos NAT gestionados por el cliente o conjuntos complejos de reglas de retorno para superponer escenarios CIDR.
  • La traducción simétrica y bidireccional gestionada por AWS reduce el riesgo de configuración errónea en comparación con los pares manuales de reglas NAT.
  • Leverages Regional Private NAT Infraestructura de puerta de entrada, heredando sus propiedades de escalada y resiliencia (limitos específicos no revelados).
  • La granularidad por regla de apego apoya la migración gradual y la traducción selectiva en grandes topologías.
  • La paridad de IaC en CloudFormation, CLI, SDKs y Console permite la integración inmediata de tuberías.
  • La integración CloudWatch y EventBridge proporciona observabilidad; los esquemas métricos y de eventos exactos requieren revisión de la documentación.

Consecuencias arquitectónicas para la conectividad híbrida y multicloud

La función beneficia directamente a tres escenarios de alto impacto citados en el anuncio: fusiones y adquisiciones, conectividad de red asociada sobre la VPN del sitio a satélite y interconexión multicloud vía Direct Connect o Transit Gateway Connect. En cada caso, el problema de CIDR superpuesto ha sido históricamente un bloqueador que retrasa la integración de la red por semanas o meses. Con 1:1 NAT sobre el apego, el cronograma de integración se desploma hasta el tiempo necesario para definir mapas de traducción y actualizar el enrutamiento, un cambio que el anuncio caracteriza como minutos.

Para arquitecturas multicloud, la capacidad de traducir en el lado AWS de un accesorio Direct Connect o VPN significa que la nube remota o la red local no necesita implementar NAT complementario. Esta asimetría simplifica las negociaciones con asociados o entidades adquiridas que puedan carecer de capacidad de los NAT o de madurez operacional. Sin embargo, el anuncio no confirma si la traducción conserva direcciones originales de origen para la inspección de registro o seguridad en el lado remoto; si la preservación IP de origen es necesaria para la detección del cumplimiento o la amenaza, los equipos deben verificar si la dirección traducida o la dirección original aparece en registros de flujo y evaluaciones de grupos de seguridad.

Los accesorios Transit Gateway Connect para electrodomésticos SD-WAN extienden el beneficio a las topologías de rama y borde donde el espacio de dirección superpuesta es común en sitios gestionados independientemente. El dispositivo SD-WAN sigue anunciando su CIDR local; la regla de traducción en el accesorio Connect lo mapea a un rango no superpuesto dentro de la tabla de ruta Transit Gateway. Este patrón permite la gestión centralizada de direcciones sin redes de rama de re-IPing. El límite práctico será el número de reglas de traducción apoyadas por apego y por Transit Gateway, una cuota no revelada en la liberación.

  • Acelere la integración de la red MюA de semanas a minutos eliminando el requisito de renumeración.
  • La capacidad de traducción asimétrica simplifica el a bordo del socio; el lado remoto no necesita cambios NAT.
  • La integración SD-WAN a través de Transit Gateway Connect permite la superposición de la sucursal sin re-IPing.
  • No se confirma la visibilidad IP de la fuente para la seguridad y el cumplimiento en redes remotas; requiere validación.
  • No se han consignado cuotas por apego y reglas de traducción por vía aérea; pueden limitar los despliegues a gran escala.
